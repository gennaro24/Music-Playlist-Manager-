2. Accoppiamento — valutazione per modulo

Modulo Accoppiamento Evidenza
domain 5/5 Nessuna dipendenza verso UI/Application/Persistence. Solo Java + domain.
persistence 5/5 Dipende da Domain. Interfacce Repository + implementazioni SQLite.
application.service 4/5 Dipende da interfacce Repository (DIP). Testabili con Fake/InMemory.
application.command 4/5 Ciclo command ↔ concreteCommands (atteso nel pattern Command).
application.facade 3/5 Isola bene la UI, ma conosce molti service/command concreti.
ui 4/5 Solo Facade + Domain + JavaFX. Nessun import Persistence/Service.
bootstrap 5/5 Composition root: unico posto che collega i concreti.

3. Coesione — proxy per dimensione classe

Classi molto grandi spesso mescolano più responsabilità (bassa coesione). Soglia indicativa: >400 LOC = attenzione; >800 LOC = criticità.

Classe ~LOC Coesione Note
TrackController 1026 Bassa Catalogo + playlist + tag + dialoghi UI.
MusicPlaylistManagerFacade 464 Media Coerente col pattern Facade, ma cresciuta.
PlaybackService 428+ Media Context Strategy + stato player: ambito unico ma ampio.
PlaylistController 350 Media Ancora gestibile.
TrackService / TagService / Commands <200 Alta Una responsabilità chiara per classe.
domain.model / strategy piccole Alta Entità e algoritmi ben separati.

4. Regole ArchUnit (verifica automatica)

File

src/test/java/.../architecture/ArchitectureTest.java

Comando

mvn test -Dtest=ArchitectureTest

oppure tutti i test: mvn test

Regole controllate

  • Layered architecture (Domain / Application / Persistence / UI / Bootstrap)
  • Domain indipendente dagli altri layer
  • UI ↛ Persistence
  • UI ↛ application.service
  • Persistence ↛ UI / Application
  • Domain solo su domain + Java
  • Interfacce *Repository in persistence.repository

Se i test ArchUnit sono verdi, l’accoppiamento tra strati rispetta le regole. Se falliscono, il messaggio indica le classi che violano il design.
